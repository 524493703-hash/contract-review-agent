# 合同审核流程与租赁条款知识库设计

## 1. 结论先行

建议把当前链路从“上传合同后直接做规则/大模型审核”重构为：

```text
合同包接入与完整性校验
  -> 文档角色识别（主合同/订单/报价单/一般条款/技术附件/批注版）
  -> 合同类型、我方角色、交易场景与模板来源识别
  -> 条款树 + 原子义务 + 数值事实 + 交叉引用结构化
  -> 组合式 Playbook（基础包 + 出租方包 + 叉车/特种设备包 + 金额/场景包）
  -> 生成本次适用的 30~50 个 Focused Checks
  -> 每个 Check 独立、可追溯地召回候选条款
  -> 确定性规则先判，DeepSeek 仅处理语义和冲突
  -> 仅在法律效力、强制性规范或时点问题上查询法律 RAG
  -> MET / UNMET / PARTIAL / NOT_MENTIONED
  -> Evidence 与覆盖审计
  -> 风险分级、修改策略、Redline 草案
  -> 对修改后文本再跑一次相关 Checks
  -> 高风险人工确认后导出
```

核心原则有三条：

1. 《一般性条款》是“公司基准/谈判立场”，不是法律法规库，也不能直接等同于 49 个审核结论。
2. “不遗漏”不能靠一次向量检索的 Top-K；必须靠“所有适用 Check 强制执行 + Check/条款双向覆盖矩阵 + 无证据状态”保证。
3. “精准命中”不能把 PDF 按固定 token 长度切块；必须保留条款树，同时把长条款拆成可检索的原子义务，并从原子义务回溯完整父条款用于判断和 Redline。

## 2. 源文件核验与当前实现差距

### 2.1 源文件事实

- 文件：`4-CHN-林德（中国）叉车有限公司设备租赁合同的一般性条款--2025年01版.pdf`
- 版本：2025 年 01 版。
- 版式：单页、三栏、超密排版，共 18 章。
- 当前文本解析器得到 66 个编号记录，其中包括 1.1、2.10、11.8、12.7 等子条款，以及无子编号的第 8、10、16、18 章。
- 对 PDF 抽取文本与工程文本快照去空白后核验，两者均为 6,968 字符，相似度 1.000000；当前快照可以作为本版入库底稿，但仍须保留 PDF 为权威来源。
- PDF SHA-256：`19033CF9B75DAAF3A01BDDFC0B8F2A94BA4A1AEF74B2A747DC9479310EF8DA8D`。
- 当前工程保存的文本快照 SHA-256：`CF5A76FE35AB3D8F25300F5583E809D5C4364D0C9F6EC2BE9C13ED8E9DCD5947`。

### 2.2 当前实现中会造成漏判或误判的点

1. `StandardClause` 只有“编号、标题、全文、风险级别、是否必需”，无法表达一条内的多项义务、条件、例外、数值、责任主体和交叉引用。
2. 66 条记录仍不够原子化。例如：
   - 9.4 同时包含迟延接收日赔偿、免责例外、支付时间、三个月解除权、10% 违约金、设备先行处理及重新确定交货时间。
   - 12.2 同时包含占有使用风险、能源费用、使用单位义务、使用登记、定期检验、民事/行政/刑事责任。
   - 15.1 内含 10 个严重违约事件，但目前是一个检索块。
   - 16 和 18 都是无子编号的长条款，分别包含多个判断要素。
3. 标准模板识别后虽然逐条比较，但结果被 `[:12]` 截断；如果 13 条以上发生变化，后面的偏离不会进入结果。
4. 客户模板路径用章节关键词判断“是否缺失”。合同里只要出现“维修”二字，就可能跳过整个维修与保养检查，无法识别范围、例外或停保条件是否合规。
5. 所有基准记录均设为 `is_required=True`。定义、辅助条款、条件性条款和真正强制底线没有区分。
6. 当前知识库接口主要是数据库 `LIKE` 检索，不支持角色、概念、数值、否定、例外、条款关系和生效日期过滤。
7. “基准偏离”和“风险”混在一起。标准文本被改一个标点是偏离，但不一定是风险；客户文本不长得像标准文本，也不代表不满足公司的实质要求。

## 3. 两种审核模式必须分流

### 3.1 模板完整性模式（Template Integrity）

适用：文件被识别为林德 2025.01 一般性条款或其修改版。

- 对 66 个权威条款节点逐条比对，禁止 Top-K、禁止返回数量上限。
- 先按 `clause_no` 对齐；编号缺失时再用标题、相邻编号和语义做重定位。
- 同时做：文本归一化精确差异、数值差异、义务主体差异、否定/例外差异、删除与新增检测。
- 输出两层结论：`deviation_type`（无变化/编辑性/实质性/删除/新增）与 `risk`，不能把二者合并。
- 即使只改 `30 天`、`0.05%`、`130%`、`10%`、`30%`、`24 小时` 等一个字符，也必须进入审计结果。

### 3.2 客户合同语义审核模式（Substantive Review）

适用：客户模板、主合同、框架协议、订单或混合合同。

- 不要求客户条款与公司模板一字不差。
- 每个 Focused Check 定义“必须满足的义务槽位、可接受替代表述、禁止条件、数值底线、缺失规则”。
- 一个 Check 可以引用多处条款；一处条款也可以支撑多个 Check。
- 必须检查主合同、一般条款、订单、报价单、技术附件及官网固化条款之间的冲突和优先级。

## 4. 文档与条款的知识库分层

四类知识必须分库或至少分 namespace，检索时明确优先级：

| Namespace | 内容 | 用途 | 不允许做的事 |
| --- | --- | --- | --- |
| `company_baseline` | 公司标准模板、替代文本、谈判底线 | 判偏离、给修改建议 | 作为法律效力的最终依据 |
| `playbook` | Focused Checks、适用条件、决策规则、风险与升级规则 | 驱动审核 | 直接充当合同原文证据 |
| `legal_authority` | 现行法律、司法解释、安全技术规范及历史版本 | 回答法律效力和强制性问题 | 与公司偏好混在一个向量空间后无差别召回 |
| `precedent` | 历史合同、批准偏离、谈判结果 | 给历史参考 | 自动覆盖当前 Playbook 或作为当然放行依据 |

### 4.1 推荐的六层数据对象

1. `knowledge_document`：源文件、版本、哈希、发布日期/生效日期、适用地域、状态。
2. `clause_node`：章/条/款/项的权威树结构和完整原文。
3. `clause_atom`：一个可独立判断的义务、权利、禁止、条件、例外或定义。
4. `clause_fact`：金额、比例、期限、频率、主体、动作、对象、条件、例外等机器可比字段。
5. `focused_check`：审核问题、适用条件、证据要求、确定性规则、模型判定规则、风险与修改策略。
6. `check_baseline_map`：Check 与基准条款/原子义务的多对多关系，同时支持反向覆盖审计。

### 4.2 `clause_node` 建议字段

```json
{
  "id": "GT-2025.01-12.2",
  "document_id": "LINDE-LEASE-GT-2025.01",
  "parent_id": "GT-2025.01-12",
  "clause_no": "12.2",
  "heading_path": ["12 所有权及风险责任"],
  "order_index": 47,
  "raw_text": "……",
  "normalized_text": "……",
  "page_no": 1,
  "bbox_list": [],
  "char_start": 0,
  "char_end": 0,
  "source_hash": "……",
  "authority_level": "canonical",
  "effective_from": "2025-01-01",
  "effective_to": null,
  "language": "zh-CN"
}
```

`raw_text` 永不覆盖；清洗、纠错或重分段生成新版本。`normalized_text` 仅用于匹配，不能作为最终 Evidence 或 Redline 来源。

### 4.3 `clause_atom` 建议字段

```json
{
  "id": "GT-2025.01-13.1-A02",
  "clause_node_id": "GT-2025.01-13.1",
  "atom_type": "deemed_renewal",
  "subject_role": "LESSOR",
  "modality": "DEEMED_CONSENT",
  "action": "renew_lease",
  "object": "leased_equipment",
  "conditions": ["lease_expired", "lessee_continues_use", "lessor_no_objection"],
  "exceptions": [],
  "consequence": "original_terms_continue",
  "summary": "租期届满后继续使用且出租方无异议时视为自动续租",
  "retrieval_terms": ["自动续租", "默示续租", "继续使用", "无异议", "不定期租赁"],
  "cross_references": []
}
```

不要按 300/500 token 机械切块。嵌入向量以 atom 为主；召回后自动扩展父 `clause_node`、前后相邻条款和交叉引用条款供模型判断。

### 4.5 数值事实单独索引

至少抽取并双向校验以下字段：

```text
duration: 5工作日 / 10工作日 / 30天 / 3个月 / 24小时 / 2周
rate: 0.05%/日 / 万分之三/日 / 10% / 30% / 130%
amount_formula: 一个季度租金 / 三个月租金 / 剩余租期应付租金×30%
frequency: 每1000小时 / 每租赁年度一次 / 每月一次
condition: 逾期超过30天 / 逾期超过3个月 / 收到发票后一个月
```

统一保存 `raw_value`、`normalized_value`、`unit`、`operator`、`basis`、`scope`，避免 `30 天` 与 `一个月`、`0.05%` 与 `万分之五` 仅靠字符串比较。

## 5. Playbook 不是单选，而是组合

本次 Playbook 建议由以下包合成：

```text
LEASE_BASE_CN
+ OUR_ROLE_LESSOR
+ EQUIPMENT_FORKLIFT_SPECIAL_EQUIPMENT
+ COMPANY_BASELINE_LINDE_2025_01
+ TEMPLATE_SOURCE（公司模板 / 客户模板）
+ SCENARIO（新客户 / 老客户 / 关联方 / 官网条款 / 跨区域使用）
+ EXPOSURE（金额、期限、设备数量、信用与押金）
```

Playbook 选择前还应抽取并允许人工修正：我方合同主体、我方角色、交易类型、模板来源、设备是否属于特种设备、使用地、租期、总敞口、附件清单、是否含自动续租、是否含买断/所有权转移、客户集团主体和签约日期。

## 8. 精准召回且不遗漏的检索流程

### 8.1 每个 Check 独立召回

1. 先用元数据硬过滤：本合同、全部附件、有效版本、合同角色、合同类型。
2. 用确定性索引召回：条款编号、标题、定义词、正则、金额/比例/期限、主体动作。
3. 用 BM25 召回文字近似，用向量召回语义近似；两者做 RRF 融合，不直接相信单一相似度。
4. 命中 atom 后，扩展父条款、相邻条款、引用条款、同一概念条款和冲突附件。
5. 召回结果按 Check 的 `required_slots` 重排，而不是只按语义相似度排序。
6. 对否定、例外、但书、前置条件和“除非/不得/不影响/仅在”做单独标记。

### 8.2 不得使用全局 Top-K 作为完整性保障

可以限制“每个 Check 交给 DeepSeek 的候选数”，但不能限制“执行的 Check 数”或“模板完整性模式下的偏离总数”。候选太多时先按槽位去重；仍超长时分批判断，再做合并裁决。

### 8.3 Check/条款双向覆盖矩阵

发布 Playbook 前强制生成两张报告：

- `check -> atoms`：每个适用 Check 至少映射一个基准 atom，或显式标记 `expected_absence_check=true`。
- `atom -> checks`：每个非纯定义 atom 至少被一个 Check 使用；无人使用的条款必须标记 `informational` 或补 Check。

本文件 66 个权威条款、15.1 的 10 个子项以及所有新增 atoms 都要进入反向覆盖。任何孤儿 atom 阻止 Playbook 发布。

### 8.4 `NOT_MENTIONED` 不是“没搜到一次”

只有同时满足以下条件才可给出：

1. 合同包完整性检查通过；
2. 文档解析质量达到阈值，关键页/附件没有 OCR 或读取失败；
3. 该 Check 的确定性、BM25、向量和交叉引用召回均执行；
4. 没有候选证据填充任何核心槽位；
5. 没有因 token 截断、候选上限或模型失败跳过判断。

解析失败应使用技术状态 `UNVERIFIABLE`；Check 不适用应使用内部状态 `NOT_APPLICABLE`。二者不能伪装成 `NOT_MENTIONED`，但可以不出现在用户要求的四态业务看板中。

## 9. 确定性规则、DeepSeek 和法律 RAG 的职责边界

### 9.1 确定性规则优先

适合直接判断：编号缺失、数值变化、期限、比例、币种、签字/书面形式、特定短语、主体互换、否定词、交叉引用不存在、附件未上传、同一事实前后冲突。

### 9.2 DeepSeek 只做受约束的语义裁决

输入仅包含：角色映射、Check 定义、候选原文、父条款上下文、已抽取事实、公司基准 atoms、必要的法律材料。输出必须是 JSON：

```json
{
  "status": "PARTIAL",
  "evidence_ids": ["DOC1-C13.1-S2"],
  "satisfied_slots": ["trigger", "consent"],
  "missing_slots": ["renewal_term", "renewal_rent", "exit"],
  "contradictions": [],
  "reason": "……",
  "confidence": 0.88,
  "need_legal_rag": false
}
```

模型输出后必须程序校验：Evidence 是否为原文真实子串、角色是否一致、MET 是否填满所有强制槽位、UNMET 是否存在反向条款、NOT_MENTIONED 是否没有 Evidence、引用的数值是否与抽取值一致。失败则重试一次，仍失败转人工而不是静默通过。

### 9.3 法律 RAG 按触发器查询

只有以下情况查询：格式条款提示说明/效力、免责与责任限制、违约金调整、管辖与送达、特种设备强制义务、法定登记/检验、安全服务能否暂停、法律或规范的时点版本、模型明确标记 `need_legal_rag=true`。

法律条目必须保存：发布机关、标题、文号、条/款、原文、生效/失效日期、适用地域、官方 URL、抓取日期和内容哈希。审核时按合同签署日及履行日选版本，不能永远只检索“最新法”。例如 2026 年已有新的《特种设备使用管理规则》实施信息，证明 2025 版合同中的法规引用必须采用时点化法律 RAG，而不能永久固化为 2025 年理解。

特别注意：一般性条款 1.5 声明“不构成任何性质的格式条款”，但是否属于格式条款取决于实际拟定和协商情况，不能把该声明直接作为 MET。该 Check 应核验显著提示、说明、协商/修改痕迹和留痕证据。

## 10. 四态结论定义

| 状态 | 定义 | Evidence 要求 |
| --- | --- | --- |
| `MET` | 所有强制槽位满足，无冲突或越过底线 | 至少一条支持性 Evidence；缺失型检查除外 |
| `UNMET` | 有明确相反约定、数值越线、权利被删除或责任被转移 | 必须引用反向/偏离原文 |
| `PARTIAL` | 只满足部分槽位、表述含糊、附件冲突、条件/例外导致保护不完整 | 引用已有内容并列出缺失槽位或冲突 Evidence |
| `NOT_MENTIONED` | 在可验证且完整的合同包中未找到相关约定 | 保存完整的检索轨迹和空证据原因 |

状态只表示“是否满足 Check”，不直接等于风险。缺失通知条款可能是中风险，存在违法安全安排可能是高风险。

## 11. Evidence、风险和 Redline

### 11.1 Evidence 最小结构

```json
{
  "evidence_id": "DOC1-C12.2-S04",
  "document_id": "DOC1",
  "clause_id": "C12.2",
  "page_no": 1,
  "start_offset": 120,
  "end_offset": 186,
  "quote": "……",
  "evidence_type": "support|contradict|context|missing_trace",
  "retrieval_methods": ["number", "bm25", "vector", "cross_reference"]
}
```

Evidence 必须指向原始文档坐标；不能只保存模型概括。多处共同形成结论时全部保留，Redline 使用父条款完整范围。

### 11.2 风险建议

采用“预设基础严重度 + 交易暴露修正 + 发生条件 + 可修复性 + 判断置信度”的可解释矩阵，不建议用一个看似精确但无法复核的总分替代法律判断。每条风险至少输出：影响对象、触发场景、最坏后果、公司底线、是否可谈、需要哪个部门确认。

高风险人工门槛至少覆盖：主体/授权、所有权、特种设备安全、无限或异常赔偿、关键免责、单方调价、自动续租、提前终止损失、设备收回、重大违约、争议解决、格式条款效力以及法律 RAG 冲突。

### 11.3 Redline 生成顺序

1. 优先复用已批准的公司标准条款；
2. 次选 Playbook 中批准的 fallback/谈判版；
3. 最后才让 DeepSeek 起草，且必须满足 required slots 与禁止项；
4. 保留原编号、术语、主语和交叉引用；
5. 修改后将候选文本写入内存副本，重跑受影响 Check、引用完整性和数值一致性；
6. 高风险只生成草案，不自动接纳或覆盖原文件。

## 13. 质量门禁与测试集

### 13.1 入库门禁

- 18 个一级章节全部存在；66 个当前权威节点全部可回溯原文。
- 显式编号连续性通过，15.1 的 10 个枚举项全部拆出。
- 原文字符覆盖率不低于 99.5%（排除页眉页脚与纯空白）。
- 所有金额、比例、期限和频率完成数量抽取；抽取值与原文可逆关联。
- 所有 `4.2 -> 4.3`、`13.2 -> 15.2` 等显式引用均能解析；悬空引用阻止发布。
- 每个非信息性 atom 至少关联一个 Check；每个 Check 至少有基准映射或缺失检查标志。

### 13.2 审核回归集

对每个 Check 至少维护五类样本：标准满足、同义满足、明确违反、部分满足、完全缺失；数值型再加边界值和单位等价样本。另维护：扫描件、三栏版式、跨页条款、编号错乱、附件冲突、同一风险多次出现、删除条款、新增不利条款和官网动态条款。

建议发布门槛：关键高风险 Check 召回率 100%，全量 Evidence 召回率不低于 98%，Evidence 原文可验证率 100%，四态判定宏平均 F1 由法务黄金集验收。指标未达标时禁止用置信度掩盖漏判。

## 15. 推荐的最终审核记录

每次审核必须冻结并可重放：合同文件哈希及附件清单、解析器版本、角色映射、Playbook 版本、49 个 Check 的适用性、候选召回轨迹、规则版本、模型名称与参数、法律条目版本、四态结论、Evidence、风险、建议、Redline、人工决定和导出文件哈希。

每个非 `MET` 结果还必须展示其 `check_baseline_map` 对应的全部公司基准依据，字段至少包括文件名、文件哈希、基准版本、条号、页码和条款原文；不得只显示“依据公司模板”或仅显示知识库记录 ID。

做到这一点后，系统才能回答三类审计问题：为什么检查这一项、为什么得出这个结论、为什么改成这段文字；也能证明某个 `NOT_MENTIONED` 是完整搜索后的结论，而不是模型或 Top-K 漏看。
